# 액팅 보드 — 업무 프로세스 보좌 설계

작성 2026-08-12 · 근거: 화이트보드 세션 + `docs/기능정리.md`(구현 기능 인벤토리)

> 목표 한 줄: **액팅팀의 권한은 그대로 두고, 일만 덜어낸다.**
> 시스템은 판단하지 않는다 — 판단에 필요한 상태를 자동으로 모아 보여주고,
> 확정된 지시를 원탭으로 전파한다.

---

## 1. 업무 프로세스 (확인된 것)

```
환자 도착 → 데스크 → [상담] → [피부 전관리] → 시술 → [회복] → [피부 후관리] → 데스크 회귀
                                                                            (수납·반납)

액팅 팀원 : 상담 이후 ~ 시술 입실 전 환자 동선 조율   (화이트보드 빨간 점선)
액팅 팀장 : 시술 구간의 환자 + 의료진 + 베드 조율     (화이트보드 파란 점선)
데스크    : 최초 분배, 최종 회귀 지점
의료진    : 팀장이 call (채널톡 등)
소통 수단 : 베가스(CRM) + 무전기
```

대괄호는 선택 단계다 (2026-08-12 확인):

- **상담**: 선택 — 데스크에서 바로 시술·전관리로 갈 수 있다. 상담만 하고 가는 방문은 희박
- **피부관리**: 전관리 / 후관리 중 **택 1**, 또는 없음
- **회복실**: 케이스마다 다름 — 예약 시점이 아니라 현장에서 결정된다
- **피부관리 단독 방문**(시술 없음)이 약 10% 존재

**문제**: 환자 동선 관리·베드 배정의 판단과 권한이 전부 액팅팀에 몰려 있어 업무 과중.

**제약** (합의된 것):

1. 베가스 API 연동은 기대하기 어렵다 → 예약·시술 정보 자동 유입 없음
2. 각 팀에게 상태값 변경을 시키면 혼란 → **상태 변경(쓰기)은 액팅팀 단일 주체 유지**
3. 핵심 기능은 이미 있는 것(추적 + 네비게이션)으로 — 신규 대형 기능 지양

---

## 2. 문제의 분해 — 액팅팀 업무는 실제로 세 가지다

디스패처(액팅팀)가 하루 종일 하는 일을 쪼개면:

| 일 | 내용 | 현재 수단 | 비중 |
|---|---|---|---|
| ① 상태 파악 | "3번방 비었어?" "김OO 지금 어디?" "원장님 아직 2번방?" | 무전으로 물어봄 / 직접 가서 봄 | **최대** |
| ② 판단·매칭 | 누구를 어느 방에, 어느 의료진과 | 머릿속 + 베가스 | 중간 |
| ③ 지시 전파 | "김OO 님 3번방으로" | 무전 + 직접 안내 | 중간 |

핵심 관찰: **①과 ③은 이미 우리 시스템이 자동으로 할 수 있는 일이다.**
①은 RTLS 가 실시간으로 알고 있고(방별 재실·체류시간), ③은 방 안내(네비)가 이미 한다.
②(판단)만 사람의 일로 남기면 된다 — 베가스 없이는 자동화할 수 없고, 하려고 해서도 안 되는 부분.

즉 액팅팀 과중의 해법은 권한 분산이 아니라 **①·③의 노동을 시스템으로 옮기고
②만 남기는 것**이다. 무전 트래픽의 대부분이 ①(폴링)이므로, 이것만 사라져도 체감이 크다.

## 3. 설계 원칙 4개

1. **단일 기록자 유지** — 쓰기(배정·이동 지시)는 액팅팀만. 다른 팀은 아무것도 입력하지 않는다.
   대신 **읽기는 전원에게** 연다. 각 팀이 스스로 보면 물어볼 일이 없다.
2. **묻지 말고 도출** — 방이 비었는지, 누가 몇 분째 있는지는 사람에게 입력시키지 않는다.
   추적 데이터에서 자동으로 파생한다. (입력시키는 순간 "입력 안 해서 틀린 보드"가 되고,
   틀린 보드는 무전보다 나쁘다)
3. **결정하지 말고 제안** — 시스템은 "시술실 2 비었음 · 시술 대기 3명 중 최장 32분: 김OO"
   까지만 보여준다. 확정은 액팅팀이 탭 한 번으로.
4. **무전기는 예외 채널로 강등** — 정상 흐름(방 비움 → 다음 환자 호출 → 도착)은 보드가
   흡수하고, 무전은 돌발 상황 전용으로 남긴다. 없애는 게 아니라 줄이는 것.

## 4. 액팅 보드 (신규 화면 1개)

직원용 패널에 추가하는 **디스패처 전용 뷰**. 지도가 "어디 있나"를 보여준다면,
보드는 "**다음에 뭘 해야 하나**"를 보여준다. 데이터는 전부 기존 서버가 이미 방송하는 것
(`pos:update`, `presence:update`, `waittime:update`, `guide:all`, `presence_logs`)의 재구성이라
서버 변경이 거의 없다.

### 4.1 방 카드 그리드 (자동 도출 — 입력 없음)

상담 1~6 · 시술/수술 · 레이저 · 피부관리 · 회복 방마다 카드 한 장:

| 상태 | 도출 방법 | 표시 |
|---|---|---|
| 비어 있음 | 그 존에 환자 비콘 없음 | 초록 + "비어 있음 N분째" |
| 사용 중 | 환자 비콘 재실 | 환자 이름 + 체류 타이머 |
| 진행 중 | 환자 + 의료진(의사/간호사 그룹) 비콘 동시 재실 | 파란 테두리 + 의료진 이름 |
| **대기 방치** | 환자 입실 후 의료진 미입실 N분 경과 | 주황 경고 — **팀장의 핵심 신호** |
| 시간 초과 | 체류가 기준 시간(방 종류별 설정) 초과 | 빨강 — 화이트보드 요구 3번 |

"환자만 들어가 있고 의료진이 안 온 방"과 "비었는데 아무도 모르는 방"이
디스패처가 무전으로 캐내던 정보의 대부분이다. 이 두 가지가 자동으로 뜨는 것이 이 보드의 반이다.

### 4.2 환자 줄 (대기 오래된 순 자동 정렬)

"대기 중" 판정은 **장소가 아니라 상태**다: 이동 지시가 걸려 있지 않고 진료가 진행 중이지
않은 사람. 대기공간 재실뿐 아니라 **복도 대기**(시술실 앞 복도에서 기다리는 흔한 경우)와
**방 안 완료 대기**(4.7)까지 전부 한 줄에 모인다 — 액팅은 이 줄 하나만 보면 된다.

| 묶음 | 조건 (자동) | 표시 |
|---|---|---|
| 대기 중 | 이동 지시 없음 + 진료 미진행 (대기공간·복도·완료 후 방 안) | 이름 · 현재 위치 · **대기 N분** (오래된 순) |
| 이동 중 | 안내 걸림(`guide:all`) + 미도착 | 이름 · → 목적지 · 경과 |
| 진행 중 | 진료 방 재실 | 이름 · 방 · 경과 |
| 위치 미상 | 자리비움 | 이름 · 마지막 위치 (분실·이탈 조기 발견) |

### 4.3 원탭 디스패치

환자 줄에서 환자 탭 → 비어 있는 방 탭 → 끝. 내부적으로 기존 `/guide` 를 그대로 호출:
환자 폰에 화살표가 뜨고, 도착하면 자동 해제되고, `navigation_logs` 에 소요시간이 남는다.
**무전 "김OO 님 3번방으로 모셔" + 구두 안내가 탭 두 번으로 대체된다.**

- 방 카드가 "비어 있음"일 때만 목적지로 활성화 → 겹치기 배정 실수 방지
- 도착/미도착이 보드에 그대로 보이므로 "갔대? 도착했대?" 무전도 소멸

### 4.4 의료진 뷰 (팀장 전용 줄) + 드래그 호출

의사·간호사 비콘은 이미 추적 중이다. 팀장 화면 상단에 한 줄:
의료진별 현재 방 · 체류 시간 · (파생) "다음 가능" 여부. 여기에 4.1의 "대기 방치" 경고가
결합되면 팀장의 의료진-방 매칭 판단이 화면 한 번 훑기로 끝난다.
`person:locate` 검색("원장님 어디")도 이미 서버에 있으므로 UI만 붙이면 된다.

**의료진 드래그 호출 (2026-08-12 추가)** — 환자 디스패치와 대칭. 팀장이 의료진 카드를
환자가 있는 방에 끌어다 놓으면 **호출** 상태가 걸린다: 의료진 카드와 방 카드에
`🔔 호출됨 · N분` 배지가 뜨고, **비콘이 실제 입실을 감지하면 자동으로 해제되며 "진행 중"으로
전환**된다 (환자 안내의 도착 자동 해제와 같은 패턴 — 지시와 이행 확인이 한 화면에서 닫힌다).
전파 채널만 다르다: 환자는 폰 화살표, 의료진은 기존 무전/구두 — 보드는 호출 사실과
이행 여부를 기록·표시한다. 호출→입실 소요도 자동 기록되어 통계가 된다.

### 4.8 모듈 배치 — 역할별 기본값 + 드래그 커스터마이징 (2026-08-12 추가)

방 그리드의 섹션(상담·시술실·수술실·레이저·피부관리·회복)은 **모듈**이다.

- **역할별 기본 순서**: 팀장 뷰는 시술 구간이 주 업무라 시술실·수술실·레이저가 맨 위,
  상담이 맨 아래. 팀원 뷰는 상담 쪽이 주라 상담·피부관리가 맨 위
- **커스터마이징**: 모듈 헤더(⠿)를 끌어 원하는 위치에 놓으면 재배치. 환자·의료진
  드래그와 달리 **확인창을 한 번 거친다** — 배치 변경은 상태 조작이 아니고 실수로
  일어나면 혼란이 크기 때문. 뷰(역할)별로 따로 저장된다
- 실제 구현 시 배치는 사용자/기기별로 서버에 저장 (브라우저 스토리지 금지 — 불변식 B-5).
  스테이션 화면도 팀별로 자기 모듈을 맨 위에 둘 수 있다

### 4.9 한 화면 원칙 + 알림 UI (2026-08-12 추가)

- **한 화면 원칙**: 보드는 스크롤 없이 한 화면에 다 들어와야 한다 — 디스패처 화면은
  훑는 화면이지 읽는 화면이 아니다. 페이지 스크롤은 없애고, 넘치면 컬럼 내부 스크롤만 허용
- **알림은 본문에서 뺀다**: 경고 배너가 본문 위에 쌓이면 방 그리드를 밀어낸다.
  알림은 **우측 상단 🔔 알림 탭**으로 — 활성 알림 수 뱃지, 미확인 알림이 있으면
  **빨간색으로 깜빡**, 클릭하면 심각한 순 전체 목록
- **신규 알림은 메신저식 팝업**: 발생 순간 우측 하단에서 카드가 슬라이드 인
  (동시 2개까지, 몇 초 후 자동 사라짐, 클릭하면 알림 탭 열림) — 놓치지 않되 화면을 안 가린다
- 방 카드 자체의 상태색(방치 주황·초과 빨강)은 그대로 유지 — 알림 탭은 요약이고
  현장(그리드)에도 같은 신호가 보인다

### 4.10 3컬럼 레이아웃 · 스테이션 세분화 · 배정 승인 (2026-08-12 추가)

**레이아웃 고정** — 전 뷰 공통 3컬럼: **환자 대시보드(좌) | 방 그리드(중) | 의료진 목록(우)**.
뷰별 차이는 모듈 순서와 권한뿐이다. **의료진 배정(드래그 호출)은 팀장 뷰에서만** 가능하다.

**스테이션 2종 분화** — 하나의 읽기 전용 화면을 담당 업무별로 가른다:

| 스테이션 | 조작 (모두 PIN 인증) |
|---|---|
| **인포·상담** | ➕ 환자 등록(이름+플랜) · 환자 이름 클릭 → 플랜 수정 · 상담실 「상담 완료」(플랜 확인 필수) · 배정 승인 |
| **피부·시술** | 행동 완료 확인(마취·시술·수술·관리·회복 완료) · 배정 승인 — 그 외 읽기 전용 |

완료 확인 버튼은 담당 스테이션에만 뜬다 (인포·상담 화면에 시술실 버튼이 섞이지 않음).

**배정 승인** — 액팅이 환자를 방에 배정하면 바로 안내가 나가지 않고, **담당 팀 스테이션
정중앙에 승인 팝업**이 뜬다 (환자 이름 · 목적지 · 플랜 · 경과 시간 · 수락/거절).

- **수락** (PIN 인증) → 그 순간 환자 폰에 화살표 안내 시작
- **거절** → 배정 취소, 환자는 대기 줄 복귀, 액팅 보드에 표시 — 방이 사실은 준비가
  안 됐다(정리 중, 기구 세팅 등)는 **현장만 아는 정보**를 반영하는 마지막 안전판
- 승인 전 상태는 전 화면에서 `⏳ 승인 대기`(방 카드 주황 점선 + 이동 중 줄 표시)로 보이고,
  **3분 이상 미응답이면 액팅에게 "승인 지연" 알림**이 뜬다
- 결과적으로 한 이동이 지시(액팅) → 수락(현장 팀) → 이행(환자 화살표) → 확인(RTLS 도착)
  네 단계로 전부 기록된다 — 무전으로는 남지 않던 것들이다

### 4.5 읽기 전용 배포 (권한 분산 없이 정보만 분산)

같은 보드를 **읽기 전용**으로 각 팀 스테이션(데스크·피부실 입구·시술부 등)의
태블릿/모니터에 띄운다. 조작 버튼이 없는 URL 하나면 된다.

- 각 팀: "다음 누구 와?" 를 스스로 봄 → 액팅팀에게 안 물어봄
- 데스크: 반납 임박(회복실 체류 종료 등)을 미리 봄
- **쓰기 권한은 여전히 액팅팀뿐** — 제약 2를 지키면서 정보 병목만 해소

> 전제: 9.1 의 인증 한 겹(기능정리.md)이 먼저다. 실명 보드를 무인증으로 벽에 걸 수는 없다.

### 4.6 무전과 보드의 역할 분담 — 무전은 없어지지 않는다

보드가 흡수하는 것은 **사실 질문과 정형 지시**다. 무전에 남는 것이 분명히 있다:

| 보드가 대체 | 무전에 남음 |
|---|---|
| "3번방 비었어?" (상태 폴링) | 환자 컨디션·특이사항 ("이분 좀 어지러워하셔") |
| "김OO 지금 어디?" (위치 질문) | 의료진의 구두 지시·순서 변경 |
| "김OO 님 3번방으로" (정형 이동 지시) | 돌발 상황 전파 |
| "도착했대?" (확인 폴링) | 보드가 현실과 어긋났을 때의 정정 |

RTLS 는 **위치와 시간은 알지만 이유와 상태는 모른다.** 존 판정에는 지연도 있다
(전환 확정 ~1초, 자리비움 판정 15초). 그래서 보드는 "사실의 단일 출처",
무전은 "맥락과 예외의 채널"로 갈라진다 — 목표는 무전 0이 아니라 **폴링성 무전의 소멸**이다.

도입도 강제 전환이 아니라 병행이다. 보드를 걸어두고 무전은 그대로 쓰게 두면,
보드가 맞는다는 신뢰가 쌓이는 만큼 "물어보기 전에 보드를 본다"로 습관이 옮겨가고
폴링 무전이 자연히 준다. 7장의 단계별 확인("무전이 실제로 줄었나")이 이 전환의 계기판이다.
거꾸로 보드가 자주 틀리면(존 판정 품질 미달) 무전이 안 줄 것이고, 그때는 다음 단계로
가지 말고 게이트웨이 배치·튜닝으로 돌아가야 한다.

### 4.7 스테이션의 쓰기 3종 — 완료 확인 · 환자 등록 · 플랜 업데이트 (2026-08-12 추가)

스테이션 화면의 쓰기는 세 가지뿐이며, 전부 "자기 팀의 사실 기록"이지 동선 조작이 아니다.

| 쓰기 | 주체 | 내용 |
|---|---|---|
| ➕ 환자 등록 | 인포팀 | 접수 시 이름 + 플랜(+ 언어) 폼 입력 → 즉시 대기 줄 표시. 코스는 액팅이 배정 시 설정 |
| 플랜 업데이트 | 상담팀 | **「상담 완료」 버튼을 누르면 플랜 확인·수정 창이 먼저 뜨고, 저장해야 완료 처리** — 상담 결과가 플랜에 반영되지 않은 채 완료되는 경우를 구조적으로 차단 |
| 행동 완료 확인 | 각 팀 | 아래 체크포인트 |

**권한 방식 (2026-08-12 결정)** — 스테이션에서 쓰기 조작을 하려면 본인 **직원 비콘
고유번호 뒷 4자리(핀번호)** 를 입력해 인증한다. 로그인 시스템 없이도 (1) 아무나 못 누르고
(2) **모든 조작이 사람 이름으로 기록**된다 — 직원이 이미 지니고 다니는 비콘이 곧 신원이므로
추가 발급물이 없다. 대조 원본은 등록된 직원 비콘 화이트리스트(`beacons`). 인증은 기기당
세션 단위로 유지하고 전환 버튼으로 교대 근무에 대응한다. **비콘 등록·관리 페이지는 추후
신설 예정** (현재는 관제의 하드웨어 등록만 존재 — 직원 비콘·핀 관리 UI가 아직 없다).
코스 표시 참고: 데스크(시작·회귀)는 모든 코스의 고정 구간이므로 코스 칩에 표시하지 않는다.

RTLS 는 **누가 어느 방에 있는지**는 알지만 **방 안에서 어느 단계까지 진행됐는지**는 모른다.
마취가 끝났는지, 상담이 끝나 이동만 남았는지는 위치로 도출할 수 없는 유일한 운영 정보다.
이 공백만 버튼 하나로 메운다.

- 액팅 오더를 수행한 팀이 스테이션 화면의 방 카드에서 **완료 확인 버튼**을 누른다.
  방 종류별 체크포인트: 상담실 `상담 완료` / 시술·수술·레이저실 `마취 완료 → 시술(수술) 완료` /
  피부관리 `관리 완료` / 회복실 `회복 완료`
- 누르는 즉시 **팀장 보드의 방 카드와 환자 줄에 배지**로 뜬다 (`✔ 마취 완료 · N분 전`)
- **마지막 체크포인트가 끝나면 상태가 바뀐다**: 방 카드는 `✔ 완료 — 이동 대기`,
  환자는 진행 중 줄에서 **대기 중 줄로 자동 이동**하고(완료 후 경과 시간이 대기 시간),
  완료된 단계는 코스에서 지워지며 다음 단계가 제안된다. "시술 끝난 사람"과
  "시술 중인 사람"이 다른 줄에 서는 것 — 액팅이 다음 배정 대상을 대기 줄 하나만 보고 고른다
- 쓰기 범위가 좁아 혼란 위험이 낮다: **자기 방·자기 행동의 완료 사실 확인 한 번**이지
  자유 상태 편집이 아니다. 순서도 강제된다(마취 완료 전에 시술 완료를 누를 수 없음).
  이동·배정 권한은 여전히 액팅팀만 갖는다 — 원칙 1의 두 번째 예외(첫째는 플랜, 5.1)
- 파생 효과: "마취 완료 후 의료진 미입실 N분" 경고가 가능해져, 단순 방치 경고(입실 후
  미입실)보다 정확한 호출 신호가 된다. 체크포인트 시각이 기록되므로 마취 대기·시술 소요가
  단계 단위로 쪼개져 통계에 남는다
- 프로토타입 반영됨 (스테이션 뷰에서 체험 가능)

## 5. 코스 태그 — 베가스 없이 가능한 최소한의 "다음 단계"

업무 확인 결과(1장) 코스는 자유 순서열이 아니라 **정형 템플릿**이다. 토글 두 개면
방문 하나가 정의된다:

| 토글 | 값 |
|---|---|
| 상담 | 유 / 무 |
| 피부관리 | 없음 / 전관리 / 후관리 |

→ 정규 코스 6종 + 변형 2종:

| 코스 | 흐름 |
|---|---|
| 상담+전관리 | 데스크→상담→전관리→시술→데스크 |
| 상담+후관리 | 데스크→상담→시술→후관리→데스크 |
| 상담만 거침 | 데스크→상담→시술→데스크 |
| 전관리 | 데스크→전관리→시술→데스크 |
| 후관리 | 데스크→시술→후관리→데스크 |
| 시술 직행 | 데스크→시술→데스크 |
| (변형) 관리 단독 ~10% | 데스크→피부관리→데스크 |
| (변형) 상담 단독 — 희박 | 데스크→상담→데스크 |

- **입력은 탭 한 번** — 배정(또는 첫 디스패치) 때 2×3 격자에서 하나 선택. 3탭도 아니고
  자유 편집도 아니다. 입력 주체는 액팅팀뿐(제약 2), 배정 단위 저장 — 반납하면 소멸
- **"다음 단계" 제안이 추측이 아니라 확정이 된다** — 코스가 정형이므로 전관리를 나선 환자의
  다음은 무조건 시술이다. 보드는 "다음: 시술 (빈 방 2)" 를 바로 띄운다
- **회복실은 코스에 넣지 않는다** — 케이스마다 달라 미리 입력할 수 없는 값이다.
  시술 후 회복실 입실이 감지되면 보드가 "회복 중"으로 자동 표시하고(묻지 말고 도출),
  회복실을 나설 때 코스의 다음 단계(후관리 또는 데스크)를 제안하면 된다
- 부서별 "다음에 올 환자" 큐가 자동 생성 → 4.5 읽기 전용 화면의 가치가 배가.
  피부팀은 "전관리 대기 2명 / 후관리 예정 3명" 을 미리 본다
- 단계별 딜레이 분석(화이트보드 벤다이어그램)이 잘 정의된다: 데스크→상담, 상담→다음,
  전관리→시술, 시술→후관리, 마지막→데스크 각 구간의 대기가 `presence_logs` 로 숫자화
- **여전히 선택 사항이다.** 안 쓰면 보드는 순수 반응형(4.1~4.4)으로도 완결 동작한다.
  다만 입력이 탭 한 번으로 줄었으므로 도입 문턱은 처음 설계보다 훨씬 낮다.

### 5.1 시술 종류와 방 종류 — 이중 입력 없이 (방 선택이 곧 입력이다)

**문제**: 시술 종류에 따라 들어갈 방 종류가 갈린다(시술실 3 · 수술실 3 · 레이저실 2).
시술 정보는 베가스 차트에만 있고 API 는 없다. 시스템이 시술명을 알아야 한다면
누군가 베가스에 있는 것을 다시 쳐 넣어야 한다 — 이중 입력, 하지 않기로 한 것.

**답: 시스템은 시술명을 알 필요가 없다.**

1. 코스의 "시술" 단계는 방 **계열 전체**(시술실+수술실+레이저실)를 묶은 한 단계다.
   보드는 그 계열의 빈 방을 종류별로 묶어 보여주기만 한다:
   `시술실 ①빈 ②사용중 ③빈 · 수술실 ①②사용중 ③빈 · 레이저 ①빈 ②빈`
2. 어느 방으로 보낼지는 **어차피 차트를 보고 있는 액팅이 정한다.** 이건 원칙 3
   (결정하지 말고 제안)이 원래 사람에게 남겨 둔 판단이다. 방 8~11개의 빈/사용 상태가
   한눈에 보이면 그 판단은 이미 쉬워져 있다.
3. 그리고 액팅이 방을 고르는 순간, 시술 계열 정보는 **방 종류로 저절로 기록된다** —
   `navigation_logs`(어디로 보냈나)와 `presence_logs`(얼마나 있었나)에 방이 남으므로,
   방 종류별 소요시간·회전율·기준시간 초과 통계가 전부 입력 0회로 나온다.

**기준 시간(6.3)도 방 종류 단위로 시작한다** — 시술실 N분 / 수술실 N분 / 레이저실 N분.
시술명 단위 정밀도가 필요해지는 날이 오면, 그때도 시술명을 입력받지 말고
디스패치 때 **예상 소요 칩**(30/60/90분, 탭 1회, 선택)을 붙이는 선에서 멈춘다.

> 원칙으로 남겨 둘 문장: **베가스에 이미 있는 정보는 다시 입력받지 않는다.**
> 시스템이 아는 것은 사람이 이미 내린 결정(어느 방으로 보냈나)뿐이고, 그것으로 충분하다.

**변경 이력 (2026-08-12, 팀장 검토 후 현장 결정)** — 위 원칙을 한 단계 완화한다.
**플랜(시술 내용) 텍스트 한 줄은 입력받기로 했다**: 접수 때 인포팀이 기입하고, 상담 후
바뀌면 상담팀이 업데이트한다. 근거: 플랜이 보드에 뜨면 액팅이 베가스를 오가지 않고
보드 안에서 배정 판단을 끝낼 수 있어, 입력 한 줄의 비용보다 얻는 것이 크다고 현장이 판단.
경계는 유지한다 — 입력은 **자유 텍스트 한 줄**(참조 정보)이며, 시술 코드·구조화 입력은
여전히 받지 않고, 방 선택·통계는 종전대로 방 종류에서 도출한다. 쓰기 주체 예외도 이것뿐:
플랜에 한해 인포팀·상담팀이 쓰고, 배정·이동 지시는 여전히 액팅팀만 쓴다.
환자 이름을 누르면 플랜이 뜬다 (프로토타입 반영됨). 배정·동선 변경은 드래그 앤 드롭.

## 6. 화이트보드 추가 요구 3건

### 6.1 비콘 환자 국가별 차별화

- 국적이 아니라 **언어**가 운영 정보다 (통역 매칭·안내 문구). 배정 시 언어 선택
  한 번(기본 한국어) → `assignments` 에 저장.
- 표시: 지도 아바타 이름표에 언어 뱃지, 보드 환자 줄에 뱃지, **외국어 환자가 상담/시술
  입실 시 통역 비콘이 그 방에 없으면 보드에 표시** (통역 그룹은 이미 추적 중이므로 파생 가능).
- 파생 효과: 환자용 앱 문구 다국어화(중국어 우선 — 통역 그룹이 이미 중국어)와 자연히 연결.

### 6.2 환자용 화장실 안내

- 직원 손을 탈 이유가 없는 유일한 안내 — **환자 앱에 셀프 버튼 하나**: `🚻 화장실`
  → 가장 가까운 공용 화장실로 기존 화살표 네비.
- 구현 메모: 현재 `isGuidableZone` 은 화장실을 제외한다(직원 디스패치 목록 기준).
  셀프 안내용 별도 허용 목록(공용 화장실 4곳)과 환자 토큰 기반 `/guide` 진입을 추가.
  직원 디스패치 드롭다운에는 안 섞는다.

### 6.3 시술실 소요시간 · 시각화

- 방 카드 타이머(4.1)가 즉답. 방 종류별 기준 시간(예: 시술 40분 / 상담 20분)을 설정
  파일에 두고 초과 시 색 변화 — 장기체류 경고(10분 고정)의 방별 버전.
- 사후 분석: `presence_logs` 가 이미 다 쌓고 있다. 방별 평균/최대 체류, 시간대 히트맵을
  일일 리포트로 (기능정리.md 10-C 와 동일 항목).

### (우측 메모) 무전기 음성 수급

무전 자체를 대체하려 하지 않는다 — 4장이 무전의 **사유**(폴링·전파)를 줄이는 접근.
남는 무전은 예외 상황용이며 그게 무전의 올바른 용도다.

| **A** | 방 카드 + 환자 줄 + 의료진 줄 (읽기 전용 보드) | 거의 없음 — 기존 방송 데이터 재구성. 방별 기준시간 설정 추가 정도 | 게이트웨이 실배치 (존 판정 품질이 보드 품질) |
| **B** | 원탭 디스패치 + 도착/비움/방치 알림 | 없음 (`/guide`·`navigation_logs` 재사용) | A |
| **C** | 읽기 전용 배포 (팀 스테이션 화면) | 읽기 전용 토큰/URL | **인증 한 겹** (기능정리.md 9.1) |
| **D** | 코스 태그 + 부서별 큐 | `assignments` 열 추가 + API 소폭 | B 정착 후, 액팅팀 의향 확인 |
| **E** | 언어 뱃지 · 화장실 셀프 안내 · 방별 기준시간 튜닝 | 소폭 | 병행 가능 |

각 단계 후 확인할 것: **무전 호출이 실제로 줄었나.** 안 줄었으면 다음 단계로 가지 말고
이유를 본다 (보드가 안 보이는 위치에 있다 / 상태 도출이 틀린다 / 습관).

## 8. 부하가 줄었는지 재는 법 (데이터는 이미 쌓인다)

| 지표 | 원천 | 의미 |
|---|---|---|
| 단계 간 대기시간 (상담→시술 등) | `presence_logs` | 딜레이 구간 — 액팅 판단 지연의 결과 지표 |
| 지시→도착 소요 | `navigation_logs.travel_sec` | 전파 효율 |
| 방 공실 시간 (비움→다음 입실) | `presence_logs` 파생 | 회전율 — 베드 배정 품질 |
| 방치 경고 발생 수·해소 시간 | 보드 이벤트 (신규) | 팀장 매칭 부하 |
| 무전 호출 수 (정성) | 액팅팀 체감 | 최종 목표 지표 |

도입 전 1~2주치 `presence_logs` 를 보존해 두면 before/after 비교가 된다.

## 9. 정해야 할 것 (개발팀 → 현장 확인)

1. **코스 태그(5장)를 쓸 것인가** — 토글 한 번(2×3 격자)으로 줄었다. 액팅팀이 받아들일지,
   아니면 순수 반응형으로 갈지
2. **각 팀 스테이션 화면 하드웨어** — 태블릿? 기존 PC 모니터? 몇 곳?
3. **언어(국가) 정보 입력 주체와 시점** — 데스크 등록 시? 액팅 배정 시?
4. **방별 기준 시간** — 시술/상담/피부/회복 각각 몇 분을 초과로 볼지 (현장 숫자 필요)
5. **보드 위치** — 직원용 패널 안의 모드 전환인지, 별도 URL(`/board`)인지
   (읽기 전용 배포를 생각하면 별도 URL 쪽이 자연스럽다)
