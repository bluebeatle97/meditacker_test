# 도면 자동화 파이프라인 — 방법론

작성 2026-08-19 · 실행 도구: `tools/build-maps.py` · 운영 절차: [README 「도면이 바뀌면」](../README.md)

> 작업 순서만 필요하면 [8장 「전체 워크플로우」](#8-전체-워크플로우--도면-받고부터-푸시까지) 로.
> 이 앞부분은 그 순서가 **왜** 그런지에 대한 내용이다.

> 한 줄 요약: **건물 도안 한 장으로 전부는 안 나온다.** 기하로 뽑을 수 있는 것과
> 사람이 판단해 줘야 하는 것의 경계가 이 문서의 내용이다. 그 경계를 흐리면 자동화가
> 조용히 틀린 답을 내고, 틀린 걸 알아채는 건 한참 뒤다.

---

## 1. 왜 파이프라인인가

단계가 아홉이고 **뒤가 앞의 출력을 입력으로 받는다.** 손으로 순서대로 치던 때 두 종류의
사고가 반복됐다:

1. **순서를 틀려서** 낡은 파일이 섞인다. 화면은 그럴듯하게 뜨므로 눈으로는 안 잡힌다.
2. **한 단계를 빼먹어서** 짝이 어긋난다 — 특히 `wall-mask.png` 와 `outside-mask.png` 는
   원래 함께 나오는 짝인데, 하나만 갈면 통행 격자가 통째로 어긋난다.

`tools/build-maps.py` 가 순서를 코드로 굳혀서 두 사고를 없앤다. 입력이 없는 단계는
건너뛰고 **무엇이 빠졌는지 이름으로 알린다** — 조용히 넘어가지 않는 것이 핵심이다.

## 2. 의존 관계

```
[사람] wall.png ──build-wall-mask──┐
                                   ├─> wall-mask.png ─┬─> (아래 전부)
[사람] wall-mask.png ──normalize───┘    outside-mask.png ┘

wall-mask + outside-mask + zones.json ──build-walkable──> walkable.json, floor.json
[사람] staff-area.png                 ──build-staff-areas──> staff-area.json
[사람] floorplan-door.png             ──build-doors──> door.json
walkable + door + zones               ──build-rooms──> rooms.json, corridor.json, private-area.json
wall-mask + outside-mask + [사람] furniture-mask ──build-tiling-map──> tiling-map.png
walkable + zones + 타일셋             ──build-pixel-map──> pixelmap.png
door.json                             ──build-door-map──> doormap.png
walkable + zones                      ──copy-demo-config──> 프론트 public/config/
전부                                  ──check-walls──> 검증
```

**입구가 둘이다.** 벽 그림(`wall.png`)에서 시작하느냐, 벽 마스크를 직접 받느냐.

| 모드 | 입구 | 쓸 때 |
|---|---|---|
| `--from-art` (기본) | `wall.png` | 2.5D 벽 그림을 사람이 그려 줄 때 |
| `--from-mask` | `wall-mask.png` | 흑백 마스크를 직접 받을 때 |

⚠️ **마스크를 받았으면 `build-wall-mask.py` 를 돌리면 안 된다.** 그건 `wall.png` 에서
마스크를 *생성*하므로 받은 마스크를 덮어쓴다. 이 함정 때문에 모드를 갈랐다.

## 3. 자동화의 경계 — 사람이 줘야 하는 다섯 가지

각 항목마다 "자동으로 해보고 실패한 기록"이 해당 스크립트 주석에 남아 있다.
**두 번 시도해서 두 번 틀린 것들이다.**

| 입력 | 무엇 | 왜 자동으로 안 되나 |
|---|---|---|
| `wall.png` 또는 `wall-mask.png` | 벽 판정 | 도면의 선 굵기로 벽을 추정하면 문짝·문 열림 궤적까지 벽이 된다. 색으로 주기로 하고 규칙을 도면 쪽으로 옮겼다 |
| `floorplan-door.png` | 문 위치 | 도면에 문이 안 그려져 있다. 기하 판별 두 번 실패 — 문틈을 빨강으로 **채우면** 덩어리 하나가 문 하나가 되어 48개가 한 번에 잡혔다 |
| `staff-area.png` | 손님 통제구역 | 방 분할로 뽑으니 환자 구역 56조합 중 42개가 서로 못 닿았다. 기준점 번지기는 층 전체가 하나로 이어졌다 |
| `furniture-mask.png` | 가구 | 안내데스크 곡선이 주변 벽과 **같은 연결 덩어리**다(실측). 형태·연결·두께 어느 것으로도 안 갈린다 |
| `zones.json` | 방 이름·앵커 | 도면 라벨을 OCR 해도 "이 방이 시술실인가 상담실인가" 는 운영 지식이다 |

**경계를 지키는 방식**: `build-maps.py` 는 이 파일들이 없으면 해당 단계를 건너뛰고
목록으로 알린다. 없는 걸 추측해서 만들지 않는다 — 추측한 값이 들어가면 그게 진실처럼
굳어서 나중에 더 비싸다.

## 4. 색으로 주는 입력 — 규칙

사람이 그리는 그림은 **색이 곧 의미**다. 굵기 추정이 없으므로 애매한 구석이 없다.

| 파일 | 색 | 뜻 |
|---|---|---|
| `wall.png` | 밝기 170↑ | 바닥 |
| | 밝기 40~169 | 벽 (발이 못 들어감) |
| | 밝기 40↓ 테두리 연결 | 건물 밖 |
| | 밝기 40↓ 안쪽 갇힘 | 붙박이 물건 (= 벽) |
| `wall-mask.png` | 흰색 | 벽 |
| `outside-mask.png` | 흰색 | 건물 밖 |
| `staff-area.png` | 자홍색 `#FF00FF` | 직원 전용 |
| `floorplan-door.png` | 빨강 `#ED1C24` | 문 (틈을 **꽉 채운다**) |
| `furniture-mask.png` | 흰색 | 가구 (벽 아닌 낮은 구조물) |

문은 **선으로 긋지 말고 틈을 채운다.** 선으로 그으면 길이가 곧 판정이 되어, 짧으면 그
틈으로 방이 새고 길면 문 두 개가 한 덩어리로 붙는다.

## 4'. 2D 도면이 이미 있고 문까지 칠했다면 — `plan-to-tiling.py`

`blueprint-extract.py` 는 벡터 PDF + CAD 레이어를 받아 ①부터 돈다. 그런데 **2D 도면
래스터가 있고 문을 사람이 칠해 놨다면** ①레이어 분리와 ⑤문 잇기는 이미 끝난 상태다.
그때는 ②③⑥⑦ 만 돌린다.

```bash
python tools/plan-to-tiling.py            # floorplan-door.png → tiling-map.png
python tools/plan-to-tiling.py --dry-run  # 숫자만 보고 쓰지 않기
```

**왜 이 래스터는 받아도 되는가.** 벡터에서 뽑아 색이 양자화된 도면이라 골조와 바닥이
색으로 정확히 갈린다 — 흰색(255)이 바닥이고 나머지가 다 골조다. 스캔처럼 두께를 재서
"이건 벽일 것이다" 를 추측하는 대목이 없다.

⚠️ **외곽선과 채움을 색으로 가르면 안 된다.** 이 도면은 구조를 *어두운 외곽선 + 회색
채움*으로 그린다. 회색을 샤프트로, 어두운 선을 벽으로 잡았다가 **벽 속이 보라색**이
됐다 — 벽도 같은 방식으로 그려져 있기 때문이다. 외곽선은 자기가 감싼 것에 속한다.
그래서 흰색이 아니면 다 골조로 묶고, 부류는 ③의 두께 규칙으로 가른다.

고트의원 실측 (1650×1591, 16.2mm/px):

| 단계 | 결과 |
|---|---|
| ② 골조 | 11.5% · 79m² (문 6m² 는 사람이 칠한 것) |
| ③ 두께 분리 | 벽 49m² · 샤프트 21m² (500mm 초과) · 데스크 3m² |
| ⑥ 방 판정 (게이트) | **39개 · 430m²** — 손그림 마스크의 38개와 맞는다 |
| ⑦ 2.5D | 벽 31px · 문 27px · 샤프트 31px · 데스크 14px |

## 5. 에셋 배치용 색 지도 (`tiling-map.png`)

AI·스크립트가 타일과 벽 에셋을 자동으로 깔 수 있게 **의미만 남긴 이미지**다.

```
초록   (0,255,0)     바닥 — 타일을 깐다
검정   (0,0,0)       건물 밖 — 아무것도 깔지 않는다

           윗면 (천장과 맞닿는 면)   정면 (세로로 서서 보이는 면)
벽         파랑 (0,0,255)            빨강 (255,0,0)
문         주황 (255,165,0)          핫핑크 (255,105,180)
샤프트     보라 (150,70,200)         진보라 (90,30,140)
```

**부류마다 윗면·정면 두 색을 짝으로 준다.** 정면이 없으면 그 부류는 위에서 내려다본
평면으로만 남아서 입체로 안 읽힌다 — 샤프트가 실제로 그랬다(정면을 빼먹어 보라색 판이
바닥에 누워 있었다). 정면 색을 벽의 빨강과 합치지 않고 따로 두는 이유는, 받는 쪽이
벽면 타일과 코어 정면(엘리베이터 문·계단 개구부)을 갈라 깔 수 있어야 하기 때문이다.
부류를 합치는 건 나중에 언제든 되지만, 한 색으로 뭉쳐 놓으면 다시 못 쪼갠다.

**중간색은 쓰지 않는다.** 섞으면 받는 쪽이 임계값을 정해야 하고, 그 임계값이 또 하나의
합의 사항이 된다 — 양쪽이 다르게 잡으면 조용히 어긋난다. 색을 정확히 비교하면 끝나게 둔다.

### 정면과 윗면을 가르는 기준 — 남쪽에 바닥이 있는가

처음엔 "위 가장자리에서 N px" 를 윗면으로 잡았다가 갈아엎었다. 그 규칙은 **세로 벽에서
틀린다** — 북쪽 끝만 윗면이 되고 긴 몸통이 전부 정면으로 찍혀서, 위에서 내려다보면
윗면이어야 할 자리에 벽면 타일이 깔린다.

2.5D 에서 정면이 보이는 건 **그 아래에 바닥이 있을 때뿐**이다. 그래서 벽 픽셀에서
**아래로** 내려가 벽이 끝날 때까지의 거리가 `--face` 이하면 정면, 나머지는 윗면이다.

    가로 벽         → 아래 띠가 정면, 위쪽은 윗면
    세로 벽         → 남쪽 끝만 정면, 긴 몸통은 윗면
    양쪽이 바닥인 벽 → 북쪽은 윗면, 남쪽은 정면

**윗면이 기본이고 정면이 예외다.** 규칙을 뒤집었을 때 비율이 정면 17.9%→8.9%,
윗면 4.8%→13.8% 로 바뀐 것이 그 증거다.

### 곡선 골조는 획이 아니라 면이다 — 빗살 메우기

손그림 `wall.png` 은 곡선 골조(안내데스크 아치)의 정면을 **세로 획 여러 개**로 그렸다.
마스크가 획 사이 밝은 틈까지 그대로 받아서, 정면/윗면 규칙을 태우면 획마다 빨강 이빨이
서고 틈으로 바닥이 새어 톱니가 된다. 곡선이 곡선으로 안 읽힌다.

그래서 `--close-slits`(기본 12px)로 **양쪽이 벽인 좁은 세로 틈만** 메운다. 실측 분포가
이 처리를 예전 실패와 갈라 준다:

| 틈 폭 | 줄 수 | 정체 |
|---|---|---|
| 2px | 1,628 | 빗살 — 메울 것 |
| 4~12px | 358 | 획 사이·이음매 |
| 41~80px | — | **문 구멍 — 건드리면 안 된다** |

12px 이하 전부가 5,389px = 벽의 0.9% 다. 예전에 상한 없이 다 메웠다가 벽이 9.7%→13.5%
로 불어난 적이 있다 — **폭 상한과 축 하나(행만)** 가 그 실패와 이 처리를 가르는 선이다.

⚠️ **메모리 안에서만 메운다.** `wall-mask.png` 을 고치면 `walkable`·`rooms`·`private-area`
가 같이 움직인다. 색 지도는 코드가 읽지 않는 산출물이므로 여기서 끝내는 게 안전하다.

⚠️ **두 아치 사이는 못 메운다.** 상단 아치(곡선 벽)와 하단 아치(데스크) 사이는 닫힌
안쪽이 아니라 **복도와 이어진 열린 공간**이다(씨드를 넣어 흘려 보면 사방으로 샌다).
데스크 발자국으로 메우려면 사람이 경계를 그려 `furniture-mask.png` 에 넣어야 한다.

### 벽과 가구는 높이가 다르다

안내데스크는 벽이 아니라 가슴 높이 책상이다. 벽과 같은 띠를 쓰면 정면이 너무 넓게 잡혀
상판이 사라진다. `furniture-mask.png` 에 칠한 곳은 `--desk-face` 를 따로 쓴다.

⚠️ **두 숫자를 높이로 직접 비교하면 안 된다.** 이 규칙은 절대 높이가 아니라 "아래로
구조물이 끝날 때까지의 거리" 를 잰다. 곡선 데스크는 세로 두께가 두꺼워서(중앙값 38px)
반으로 가르려면 38px 이 필요하다 — 벽의 24px 보다 크지만 더 높다는 뜻이 아니다.

**그래서 `--desk-face` 값은 그 형태에 묶여 있다.** 데스크를 다시 그리면 다시 계산해야
한다. 목표 비율에서 값을 거꾸로 구하는 방법:

```python
# 가구 영역 안에서 '아래로 벽 끝까지 거리' 의 중앙값 = 정확히 50% 를 가르는 두께
```

## 6. 검증 — 무엇이 통과여야 하나

마지막에 `npm run check:walls` 가 자동으로 돈다. 다섯 항목이다:

| 검사 | 뜻 | 실패하면 |
|---|---|---|
| 격자 | 통행 가능 칸에 벽 픽셀이 없다 | 아바타 발이 벽에 박힌다 |
| 스냅 | 벽/바닥 경계 칸이 바닥으로 빠져나온다 | 경계에서 좌표가 벽에 갇힌다 |
| 앵커 | 존 앵커가 벽 안에 없다 | 그 방으로 안내가 안 된다 |
| 연결 | 통행 가능 구역이 하나로 이어진다 | 갈 수 없는 방이 생긴다 |
| 통행 | 경로 300개가 벽을 가로지르지 않는다 | 경로탐색이 벽을 뚫는다 |

`build-rooms.py` 출력도 함께 본다. **여러 방이 한 덩어리로 뭉치면 벽이나 문이 빠진 것이다.**
방 개수가 줄면 `private-area.json` 도 같이 줄어 **프라이버시가 풀린다** — 실측으로
방 38→33개가 되자 수술실 1·2, 상담실 3·4의 숨김이 풀렸다.

## 7. 반영에는 재시작이 필요하다

서버는 격자를 **시작할 때 한 번** 읽어 메모리에 들고 있다. 파일만 바꾸면 화면은 그대로다.

```bash
npm run stop && npm run dev:all
```

이걸 몰라서 "안 고쳐졌다" 를 두 번 겪었다. `build-maps.py` 가 끝날 때 이 문장을 다시 찍는다.

## 8. 전체 워크플로우 — 도면 받고부터 푸시까지

### 0단계 · 설계도면 → 벽·문·방·2.5D (**자동 — 벡터 레이어 도면만**)

```bash
python tools/blueprint-scale.py <mask.png> --dpi 150 --pdf <도면.pdf>   # 먼저 축척 확정
python tools/blueprint-extract.py <도면.pdf> --out <폴더> --mm-per-px 19.779
```

`blueprint-extract.py` 가 레이어 분리 → 벽 골조 → 샤프트 분리 → 창문 봉함 → 문 잇기 →
**방 판정 게이트** → 2.5D 까지 한 번에 돈다. 게이트가 실패하면 0 이 아닌 코드로 멈춘다.

실측(고트의원 도면, A3 벡터 PDF · CAD 레이어 30개):

| 단계 | 결과 |
|---|---|
| 레이어 분리 | 벽 `F-WALL1`·`F-WALL2` / 문 `F-DOOR` / 창 `F-WIN`·`A-WIN` |
| 샤프트 분리 | 21덩어리 111m² (두께 500mm 초과 = 벽이 아니다) |
| 창문 봉함 | 40곳 |
| 문 잇기 | 52개 중 확정 44 · 의심 5 · 실패 3 |
| **방 판정 게이트** | **통과 — 방 27개 467m²** |
| 2.5D | 정면 깊이 — 벽 26px · 문 23px · 샤프트 26px |

#### 두 가지 핵심 결정 (둘 다 실패를 거쳐 나왔다)

**문은 문짝 위치로 만들지 않는다.** 도면은 문을 **열린 상태**로 그린다 — 슬라이딩이 벽 속
포켓에 들어가 문틀 자리는 빈 구멍이고 문짝은 그 옆에 있다. 문짝 위치를 문틀로 쓰면 어긋난다
(세 번 틀렸다). 문짝 주변에서 **벽 덩어리 두 개**를 찾아 가장 가까운 두 점을 잇는다. 추측이
없으므로 어긋날 여지가 없다 — **방 1개 → 27개**가 이 변경 하나로 갈렸다.

**정면 깊이는 두께가 아니라 높이에서 나온다.** 119mm 가벽과 336mm 구조벽은 둘 다 천장까지
올라가므로 겉보기 높이가 같다. 두께 배수(1.6)로 잡았다가 얇은 벽이 낮아져 갈아엎었다.
깊이 = 실제 높이 × `projectionFactor`.

#### 사람이 고치는 지점은 문 하나다

문 결과를 **사람이 칠하는 그림과 같은 형식**(`floorplan-door.png`, `#ED1C24` 채움)으로 낸다.
빠진 문을 칠하고 잘못된 문을 지우면 뒷단은 그대로 돈다. `door-review.png` 가 상태를 색으로
표시한다 — 초록 확정 / 노랑 의심 / 빨강 실패, 좌표와 이유까지 함께.

#### 래스터 스캔은 거부한다

벡터 레이어가 없으면 도구가 그 자리에서 멈춘다. 억지로 두께 필터로 뽑았더니 테두리와 기둥만
나온 그림이 **그럴듯하게** 나와서 한참 뒤에 틀린 걸 발견했다. 열화된 자동 경로는 없는 게 낫다.

#### 도면 형식별 판단

| 형식 | 판단 |
|---|---|
| 벡터 (DWG·DXF·벡터 PDF) | **해볼 만하다.** `WALL`·`COLUMN` 레이어를 골라 폴리곤으로 뽑고 정해진 두께로 다시 그리면 2D 구조도가 된다. 치수선·가구는 레이어째 버린다 |
| 래스터 (스캔·이미지) | **사람이 칠하는 게 빠를 수 있다.** 벽·문이 같은 얇은 선이라 두께로 가리는 방식은 이 저장소에서 이미 실패했다(문짝·문 열림 궤적까지 벽이 됐다) |

#### 남은 것

⚠️ **기둥은 아직 별도 부류가 아니다.** 지금은 두께 필터에 걸려 샤프트로 들어간다 — 통행
불가라는 점과 정면이 붙는다는 점은 맞지만, 코어와 같은 에셋을 받는다. 갈라내려면 0단계에서
분류하고 5장의 색표에 짝(윗면·정면)을 하나 더 줘야 한다.

⚠️ **정면은 남쪽 한 방향만 그린다.** 색 지도는 시점이 하나인 투영이라 동·서·북면은 없다.
사방이 노출된 기둥이나 독립 칸막이는 이 한계가 벽보다 크게 보인다.

### 1단계 · 벽 마스크 준비

두 갈래다. **어느 쪽인지 먼저 정해야 한다** — 잘못 고르면 입력이 덮어써진다.

```bash
# (A) 2.5D 벽 그림을 사람이 그려 줬다  →  wall.png 이 원본
python tools/build-maps.py

# (B) 흑백 벽 마스크를 직접 받았다      →  wall-mask.png 이 원본
python tools/build-maps.py --from-mask
```

`--from-mask` 는 받은 마스크를 8비트 흑백으로 정규화하고(RGBA·안티에일리어싱 정리), 짝인
`outside-mask.png` 를 그 마스크 기준으로 다시 뽑는다. 짝을 안 맞추면 통행 격자가 어긋난다.

### 2단계 · 파이프라인 실행

```bash
python tools/build-maps.py --from-mask --dry-run   # 무엇이 돌지 먼저 확인
python tools/build-maps.py --from-mask
```

8단계가 순서대로 돌고, 사람이 그려 줘야 하는 입력이 없으면 그 단계를 건너뛰며 **파일명으로**
알린다. 끝에 `check:walls` 가 자동으로 돈다.

띠 두께를 조정할 때:

```bash
python tools/build-maps.py --from-mask --face 24 --desk-face 38
```

### 3단계 · 검증 게이트

**두 곳을 본다. 하나라도 어긋나면 커밋하지 않는다.**

**(가) `check:walls` 다섯 항목** — 6장 표 참고. 앵커 실패는 그 방으로 안내가 안 되는 것이므로
반드시 고친다. 단, 이미 있던 실패는 이번 변경 탓이 아니니 이전 상태와 비교해서 판단한다.

**(나) `build-rooms.py` 출력의 방 개수** — 여기가 진짜 함정이다.

```
조각 42개 · 방 38개 · 여러 방이 뭉친 조각 1개    ← 정상
조각 35개 · 방 33개 · 여러 방이 뭉친 조각 2개    ← 벽이나 문이 빠졌다
```

방이 뭉치면 `private-area.json` 이 같이 줄어 **프라이버시가 풀린다.** 실측으로 방 38→33개가
되자 수술실 1·2, 상담실 3·4 의 숨김이 풀렸다 — 통행 검사는 전부 통과한 상태였다. 즉
**통행이 정상이라고 방 분할도 정상인 건 아니다.**

뭉쳤으면 `room-preview.png` 를 열어 본다 (초록=복도, 파랑=방, 주황=뭉침, 빨강=문). 새는
자리가 눈에 바로 보인다. 그 자리가 **문이면** `floorplan-door.png` 에 채우고, **벽이 빠진
것이면** 마스크를 고친다. 벽에 뚫린 구멍은 메우는 게 아니라 문으로 등록하는 것이 맞는
경우가 많다 — 통행은 열려 있어야 하고 분할만 막혀야 하기 때문이다.

### 4단계 · 서버 재시작 후 눈으로 확인

```bash
npm run stop && npm run dev:all
```

서버는 격자를 **시작할 때 한 번** 읽는다. 파일만 바꾸면 화면은 그대로다.
직원 화면에서 `🚧 통제구역 보기` 로 벽이 도면과 맞는지, 환자 화면에서 아바타가 벽에
박히지 않는지 본다.

### 5단계 · 커밋·푸시

**main 에 직접 올린다** (이 저장소는 기능 브랜치를 쓰지 않는다).

```bash
git add README.md docs/ tools/ packages/server/src/config/
git commit    # 메시지는 아래 참고
git push origin main
```

커밋에 **같이 들어가야 하는 것** — 입력과 파생물이 한 커밋에 있어야 나중에 되돌릴 수 있다:

| 종류 | 파일 |
|---|---|
| 손으로 준 입력 | `wall.png` 또는 `wall-mask.png`, `floorplan-door.png`, `staff-area.png`, `furniture-mask.png` |
| 파생물 | `outside-mask.png`, `walkable.json`, `floor.json`, `rooms.json`, `corridor.json`, `private-area.json`, `staff-area.json`, `door.json`, `tiling-map.png` |
| 미리보기 | `room-preview.png`, `door-preview.png` |

⚠️ **`gateways.json` 은 빼는 게 안전하다.** 게이트웨이를 UI 에서 등록·이동하면 서버가
런타임에 이 파일을 쓴다(`applyGateways`). 도면 작업과 무관한 변경이 섞여 있을 수 있다.

메시지에는 **숫자를 남긴다.** 나중에 회귀를 판단하는 기준이 그 숫자다:

```
벽 마스크 교체 — 통행 49.9%, 방 33개

- 통행가능 81,561칸 (이전 49.6% → 49.9%)
- 방 38개 → 33개: 수술실 1·2, 상담실 3·4 가 복도로 샜다
  → 그 자리는 문이므로 door.json 등록으로 해결 예정
- check:walls 앵커 1건 실패(탕비공간 2)는 이전에도 있던 것
```

### 되돌리기

파생물은 전부 추적되므로 한 줄로 돌아간다:

```bash
git checkout -- packages/server/src/config/
```

커밋한 뒤라면 그 커밋만 되돌린다. **입력과 파생물을 한 커밋에 넣는 이유가 이것이다** —
갈라 놓으면 마스크는 새 것인데 격자는 옛 것인 상태가 만들어진다.
